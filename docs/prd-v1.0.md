# 微型工单系统 PRD v1.0

| 项目 | 内容 |
| --- | --- |
| 文档版本 | v1.0 |
| 编写日期 | 2026-09-07 |
| 文档状态 | 需求草案，待确认；不代表功能已经实现 |
| 产品定位 | 面向单个小团队的问题反馈与处理工具 |
| 学习定位 | 帮助熟练使用 Vue 的前端开发者完成第一个后端业务闭环 |
| 首版规模 | 3 种角色、4 种工单状态、4 个页面、4 类核心数据 |

## 1. 背景与目标

### 1.1 要解决的问题

小团队通过聊天工具反馈问题时，容易出现问题遗漏、责任不清、处理过程无法追溯，以及“处理人认为解决了，提单人却认为没有解决”的情况。

本产品将问题记录为工单，明确提交者、当前处理人、处理状态和沟通记录，形成可以追踪和验收的闭环。

### 1.2 产品目标

- 提单人能够提交问题，查看进度，补充信息，并确认是否解决。
- 管理员能够查看全部工单，分配或调整处理人。
- 处理人能够查看分配给自己的工单，沟通问题并提交解决说明。
- 参与者能够在工单详情中看到完整的沟通和状态变化历史。

### 1.3 学习目标

首版不仅要“页面能操作”，还要练习以下能力：

- 设计数据关系、业务接口、输入校验和统一错误反馈。
- 区分登录认证、角色权限与具体数据的访问权限。
- 使用服务端规则约束状态变化，而不是依赖前端隐藏按钮。
- 保证关联写入的一致性，并处理重复操作和并发修改。
- 完成真实数据库持久化、前后端联调、关键业务测试和可复现运行。

### 1.4 完成定义

使用不同账号，通过真实后端接口与数据库完成以下流程，并通过本文的 P0 验收场景：

> 提交工单 → 管理员分配 → 沟通处理 → 提交解决说明 → 提单人确认关闭。

同时支持“提单人不认可解决结果，将工单退回处理”的分支。

## 2. 首版假设与范围

### 2.1 本文采用的默认假设

1. 仅服务一个团队，不区分组织、租户、部门或项目空间。
2. 每个账号只有一种角色，首版不支持角色切换或自定义权限。
3. 使用预置账号完成业务验证，不开放注册和账号管理。
4. 一个工单同时只有一位提单人和最多一位当前处理人。
5. 标题、描述、评论、解决说明均为纯文本，不支持附件或富文本。
6. 桌面端优先，移动端不作为首版验收门槛。
7. 前端沿用现有 Vue + TypeScript 项目；后端语言、框架和数据库产品另行确定。

以上为控制学习范围而作出的产品选择，确认前可以调整，不是现有系统的既成能力。

### 2.2 P0：1.0 必须完成

| 功能域 | 首版内容 |
| --- | --- |
| 身份认证 | 登录、退出、恢复当前登录身份、会话失效处理 |
| 工单提交 | 填写标题、描述、分类和优先级，生成工单编号 |
| 工单查询 | 按角色限制可见范围，支持搜索、筛选、分页和详情 |
| 分配处理 | 管理员首次分配和处理中改派 |
| 沟通记录 | 工单参与者添加纯文本评论 |
| 状态流转 | 解决、退回处理、确认关闭 |
| 过程追踪 | 记录创建、分配、改派和状态变化事件 |
| 交付验证 | 真实数据库、关键接口测试、初始化数据与运行说明 |

### 2.3 明确不进入 1.0

- 公开注册、找回密码、用户管理页面、角色编辑。
- 多租户、多部门、多人协作处理、关注人和抄送人。
- 自定义表单、自定义流程、审批流、SLA 和自动催办。
- 附件上传、图片粘贴、Markdown、富文本、私密内部备注。
- 邮件、短信、站内通知、WebSocket 实时推送。
- 数据看板、图表统计、导入导出、全文搜索服务。
- 工单删除、撤销、自动关闭，以及关闭后的重新打开。
- 微服务、消息队列、独立缓存服务和高并发架构。

## 3. 用户角色与权限

### 3.1 角色定义

| 角色 | 标识 | 职责 | 可见工单 |
| --- | --- | --- | --- |
| 提单人 | `REQUESTER` | 提交问题、补充信息、验收结果 | 自己提交的工单 |
| 处理人 | `AGENT` | 处理被分配的问题、提交解决说明 | 当前分配给自己的工单 |
| 管理员 | `ADMIN` | 全局查看、分配和改派 | 全部工单 |

管理员在首版承担“调度员”职责，不代替处理人解决，也不代替提单人验收。处理人、管理员不兼任提单人；需要体验其他角色时使用对应账号。

### 3.2 权限矩阵

| 操作 | 提单人 | 处理人 | 管理员 |
| --- | --- | --- | --- |
| 创建工单 | 允许 | 不允许 | 不允许 |
| 查询列表和详情 | 仅本人提交 | 仅当前分配给本人 | 全部 |
| 添加评论 | 本人工单且未关闭 | 当前负责工单且未关闭 | 任意未关闭工单 |
| 首次分配 | 不允许 | 不允许 | 仅待分配工单 |
| 改派处理人 | 不允许 | 不允许 | 仅处理中工单 |
| 标记已解决 | 不允许 | 当前负责且处理中的工单 | 不允许 |
| 退回处理 | 本人提交且已解决的工单 | 不允许 | 不允许 |
| 确认关闭 | 本人提交且已解决的工单 | 不允许 | 不允许 |
| 修改原始内容或删除工单 | 不允许 | 不允许 | 不允许 |
| 编辑或删除评论、事件 | 不允许 | 不允许 | 不允许 |

补充规则：

- 所有权限均由后端校验，前端按钮显隐仅用于交互提示。
- 工单改派后，原处理人立即失去该工单的读取和操作权限，即使曾参与评论或处理。
- 新处理人能够读取该工单已有的全部评论和事件。
- 评论和事件继承所属工单的读取权限，不存在独立的公开访问入口。

## 4. 工单状态与业务流程

### 4.1 状态定义

| 状态 | 标识 | 含义 | 处理人要求 |
| --- | --- | --- | --- |
| 待分配 | `PENDING` | 已提交，尚未明确处理人 | 必须为空 |
| 处理中 | `IN_PROGRESS` | 已有处理人，问题尚未被标记解决 | 必须有处理人 |
| 已解决 | `RESOLVED` | 处理人已提交解决说明，等待提单人验收 | 保留处理人 |
| 已关闭 | `CLOSED` | 提单人确认解决，流程结束 | 保留处理人 |

“已解决”不等于“已关闭”。管理员分配后直接进入“处理中”，首版不增加接单或开始处理步骤。

### 4.2 允许的状态变化

| 当前状态 | 操作 | 发起者 | 目标状态 | 附加要求 |
| --- | --- | --- | --- | --- |
| 无 | 创建工单 | 提单人 | 待分配 | 必填字段校验通过 |
| 待分配 | 分配处理人 | 管理员 | 处理中 | 选择一个处理人账号 |
| 处理中 | 改派处理人 | 管理员 | 处理中 | 新旧处理人不同，填写改派原因 |
| 处理中 | 标记已解决 | 当前处理人 | 已解决 | 填写解决说明 |
| 已解决 | 退回处理 | 原提单人 | 处理中 | 填写退回原因，处理人保持不变 |
| 已解决 | 确认关闭 | 原提单人 | 已关闭 | 二次确认 |

未列出的状态变化全部禁止。已关闭工单为只读终态，不能评论、改派或重新打开；后续出现新问题应新建工单。

### 4.3 典型使用路径

1. 提单人登录，创建工单，获得唯一编号并进入详情页。
2. 管理员在待分配列表中找到工单，指定处理人。
3. 处理人查看详情，必要时通过评论询问；提单人补充信息。
4. 处理人填写解决说明，将工单标记为已解决。
5. 提单人验证结果：认可则关闭，不认可则填写原因退回处理。
6. 若被退回，当前处理人继续处理，再次提交新的解决说明。

## 5. 页面范围与交互

### 5.1 四个页面

以下为建议前端路由，不限定具体路由库实现。

| 页面 | 建议路由 | 主要内容 |
| --- | --- | --- |
| 登录页 | `/login` | 账号、密码、登录按钮、失败提示 |
| 工单列表页 | `/tickets` | 角色对应的列表标题、搜索筛选、工单表格、分页 |
| 新建工单页 | `/tickets/new` | 标题、描述、分类、优先级、提交和取消；仅提单人可访问 |
| 工单详情页 | `/tickets/:id` | 工单内容、参与者、状态操作、评论和事件时间线 |

### 5.2 公共区域

- 登录后显示当前昵称、角色和退出入口，不增加独立个人中心。
- 提单人的列表标题为“我提交的工单”，处理人为“分配给我的工单”，管理员为“全部工单”。
- 页面和接口请求分别处理加载中、无数据、失败、无权操作和会话失效状态。
- 提交期间禁用对应按钮；失败保留用户输入，成功后以服务端返回的数据更新界面。
- 不可执行的业务操作不显示入口；若页面已经过时，后端拒绝后提示刷新当前工单。
- 列表不轮询、不实时推送，提供手动刷新；成功执行操作后主动更新相关数据。

## 6. 功能需求

### FR-01 登录与会话

- 使用账号和密码登录；登录成功后进入工单列表。
- 账号不存在和密码错误统一提示“账号或密码错误”，不区分具体原因。
- 页面刷新后可恢复当前身份，但身份和权限以服务端验证结果为准。
- 首版会话有效期固定为登录后 2 小时，不提供“记住我”和自动续期。
- 会话失效时提示“登录已失效，请重新登录”，返回登录页，不自动重放未完成的写请求。
- 退出必须使本次会话在服务端失效；旧凭证不能继续访问受保护接口，不影响其他独立会话。
- 本地初始化至少提供 5 个账号：提单人 A/B、处理人 A/B、管理员，用于跨账号权限测试。
- 初始化方式、账号标识写入后续运行说明；真实密码不写入代码仓库，公开环境不得沿用公开演示凭证。

### FR-02 创建工单

| 输入字段 | 是否必填 | 规则 | 默认值 |
| --- | --- | --- | --- |
| 标题 | 是 | 5～100 个字符，单行 | 空 |
| 问题描述 | 是 | 10～5000 个字符，允许换行 | 空 |
| 分类 | 是 | 问题反馈、功能建议、其他 | 问题反馈 |
| 优先级 | 是 | 低、普通、高 | 普通 |

- 文本长度以去除首尾空白后的 Unicode 码点数计算；纯空白不视为有效输入。
- 分类和优先级使用固定枚举，首版不提供配置页面；优先级仅用于展示和筛选，不触发 SLA。
- 服务端生成内部 ID、工单编号、提单人、状态和时间；初始状态为待分配，处理人为空。
- 工单编号采用 `TK-` 加至少 6 位数字，例如 `TK-000001`，唯一、不可修改，允许跳号，不按日期重置。
- 创建请求只接受上述 4 个业务字段；注入提单人、处理人、状态等服务端管理字段时拒绝请求。
- 成功后跳转详情页；失败保留已填写内容并定位字段错误。
- 提交成功后不允许修改原始标题、描述、分类和优先级，补充或纠正信息通过评论完成。

### FR-03 工单列表与查询

- 查询范围严格遵循角色权限，先限定可见工单，再搜索、筛选、排序和分页。
- 列表字段：编号、标题、分类、优先级、状态、提单人、当前处理人、创建时间、最后更新时间。
- 支持按标题或工单编号进行不区分英文字母大小写的包含搜索；关键词去除首尾空白，最多 100 个字符。
- 支持状态、分类和优先级筛选；管理员额外支持按处理人筛选，包括“未分配”。
- 不同筛选条件为“且”关系；空关键词不增加搜索限制。更改条件后回到第 1 页。
- 固定按创建时间倒序，同一创建时间按内部 ID 倒序，不随评论更新而改变排序规则。
- 页面每页 20 条；接口必须执行服务端分页，单次最多返回 100 条，超过限制返回参数错误。
- 总数仅统计当前用户有权查看且匹配条件的数据，不泄露全局数量。
- 无匹配数据时显示空状态；请求超出末页时返回空列表及正确总数，前端允许返回有效页码。

### FR-04 工单详情

- 展示原始内容、编号、分类、优先级、状态、提单人、当前处理人和创建/更新时间。
- 按当前身份及状态提供分配、改派、解决、退回或关闭入口。
- 统一时间线展示评论和系统事件，显示操作者、时间、内容及必要的变化前后信息。
- 时间线默认加载最新 20 条并倒序展示，支持“加载更早记录”；同一时间使用服务端稳定顺序。
- 每次解决说明均作为历史事件保留；退回后不能覆盖或删除此前的解决说明。
- 所有内容按纯文本显示，输入中的 HTML 或脚本不得作为可执行内容渲染。

### FR-05 分配与改派

- 仅管理员可操作；候选列表只返回角色为处理人的账号。
- 首次分配仅允许对待分配工单执行，成功后进入处理中。
- 改派仅允许对处理中工单执行，必须填写 1～500 字符的原因。
- 新处理人不得为空、不得是提单人或管理员账号，也不得与当前处理人相同。
- 改派不改变工单状态，记录原处理人、新处理人、操作者和原因。
- 已解决、已关闭工单不能改派；已解决工单需先由提单人退回，才能按处理中规则改派。

### FR-06 评论

- 有权限的用户可对未关闭工单添加评论，长度为 1～1000 个字符，文本计数规则同 FR-02。
- 评论作者和发布时间由服务端确定，不接受客户端冒充作者。
- 评论成功后追加到时间线，并更新工单的最后更新时间，不改变工单状态。
- 评论不支持编辑、删除、回复层级、提及用户或私密可见范围。
- 评论与关闭并发时，以服务端实际提交顺序为准；关闭生效后不得再写入评论。

### FR-07 解决、退回与关闭

- 解决：当前处理人对处理中工单填写 1～2000 字符的解决说明，成功后状态为已解决。
- 退回：原提单人对已解决工单填写 1～1000 字符的退回原因，成功后状态为处理中，保留当前处理人。
- 关闭：原提单人对已解决工单二次确认后关闭，确认文案说明“关闭后无法继续评论或重新打开”。
- 状态操作必须同时校验当前角色、数据权限、旧状态和流程版本。
- 不提供任意修改 `status` 的通用编辑能力，不能通过客户端自行指定目标状态绕过业务动作。

### FR-08 系统事件

- 必须记录创建、首次分配、改派、标记已解决、退回处理、确认关闭。
- 事件包含所属工单、操作者、发生时间、事件类型，以及该操作涉及的前后状态、前后处理人、说明或原因。
- 工单业务修改和对应事件必须共同成功或共同失败，禁止出现“状态已变但事件丢失”。
- 评论作为独立记录合并显示在时间线中，不再生成一条重复的评论系统事件。
- 所有角色均不能手动修改或删除事件；失败请求不生成成功业务事件。

## 7. 数据与接口能力边界

### 7.1 核心数据概念

以下是概念模型，不是最终数据库建表脚本；字段类型、索引和具体关联方案在技术设计阶段确定。

| 数据 | 核心信息 | 关系与约束 |
| --- | --- | --- |
| 用户 `User` | ID、账号、密码哈希、昵称、角色、创建时间 | 账号唯一；角色为固定枚举；密码及其哈希不得返回前端 |
| 工单 `Ticket` | ID、编号、标题、描述、分类、优先级、状态、提单人、当前处理人、流程版本、创建/更新时间 | 编号唯一；关联一个提单人及零或一个处理人 |
| 评论 `Comment` | ID、工单、作者、正文、创建时间 | 归属一个工单，作者来自已认证身份 |
| 事件 `TicketEvent` | ID、工单、操作者、类型、变化详情、创建时间 | 归属一个工单，保存业务变化历史 |

- 工单创建时流程版本为 1，每次成功分配、改派或状态流转递增；普通评论不改变流程版本。
- 创建、评论、分配、改派和状态变化均维护工单最后更新时间。
- 业务时间由服务端生成，接口返回带时区信息的时间值；页面按浏览器本地时区展示。
- 首版不支持删除这些业务记录，不引入回收站或软删除流程。

### 7.2 后端需要提供的能力

- 登录、退出、获取当前已认证用户。
- 查询可分配的处理人账号，仅管理员可调用。
- 创建工单、查询权限范围内的工单列表与详情。
- 首次分配、改派、解决、退回、关闭等独立业务动作。
- 添加评论、分页查询有权限工单的时间线。

具体接口 URL、请求结构、认证方式和框架不在本 PRD 中锁定，后续技术方案必须保留上述权限和业务语义。

## 8. 一致性、并发与异常处理

### 8.1 一致性要求

- 待分配工单必须没有处理人；其他状态必须存在有效处理人。
- 创建工单与创建事件、后续流程修改与对应事件必须原子提交。
- 同一旧流程版本被两个请求同时修改时，最多一个成功；另一请求提示冲突，不静默覆盖。
- 角色、当前处理人、状态和版本校验必须与写入保持一致，不能只在请求开始时检查一次。
- 同一次解决被重复提交时，不得重复流转或产生多条成功事件。

### 8.2 用户可理解的错误反馈

| 场景 | 接口状态 | 页面反馈 |
| --- | --- | --- |
| 字段缺失、超长、枚举错误或注入禁止字段 | `400` | 显示具体字段问题，保留输入 |
| 登录凭证错误、未登录、会话过期或已退出 | `401` | 登录页提示错误；受保护页面引导重新登录 |
| 能读取工单，但当前角色不能执行该动作 | `403` | “你没有执行此操作的权限” |
| 工单不存在，或不在当前用户可见范围内 | `404` | 统一提示“工单不存在或不可访问” |
| 状态不允许、流程版本已过时、重复状态操作 | `409` | “工单状态已变化，请刷新后重试” |
| 服务端意外失败 | `500` | “操作失败，请稍后重试”，不暴露内部异常 |
| 网络中断或超时，结果无法确认 | 无确定响应 | 提示核对列表或时间线后再决定是否重试 |

资源操作按“是否登录 → 是否可读取该工单 → 是否有动作权限 → 状态和版本是否有效”的顺序判断；例如改派后的原处理人访问该工单返回 `404`。

### 8.3 重试边界

- 前端提交中禁用按钮，不自动重试创建、评论和状态变更请求。
- 因超时无法确认结果时，不能直接断言操作失败，也不能自动再创建一条记录。
- 首版通过状态和流程版本防止重复状态变更；创建与评论暂不提供通用幂等键，不承诺重发请求只产生一条记录。
- 通用幂等机制作为后续学习扩展，不把“前端按钮禁用”等同于服务端防重保证。

## 9. 非功能要求

### 9.1 安全与数据隔离

- 受保护接口必须验证服务端登录身份，不能信任客户端传入的用户 ID 或角色。
- 密码不得明文存储；密码、密码哈希、会话凭证不得出现在普通接口响应或业务日志中。
- 工单、评论和事件查询使用同一套数据可见性规则，不能通过独立子资源接口绕过。
- 服务端校验所有输入，前端校验用于改善体验而非替代后端检查。
- 不向用户暴露数据库语句、堆栈、内部连接信息等调试内容。
- 公开部署前启用 HTTPS，并在技术方案中落实登录尝试限制、凭证安全存放及与认证方案匹配的跨站请求防护。

### 9.2 数据与可用性

- 数据存入真实数据库，不以浏览器本地存储或内存 Mock 作为最终实现。
- 页面刷新、退出登录、后端服务重启后，已经成功提交的数据仍然存在。
- 列表和时间线使用服务端分页；1.0 不设置高并发或大规模吞吐验收指标。
- 网络失败可恢复，表单失败保留输入，不因刷新展示状态而重复提交数据。

### 9.3 可维护与可运行

- 提供初始化脚本或等效命令，能够建立开发账号和演示数据，重复执行不得产生重复账号。
- 提供环境变量示例和运行说明，但不包含真实密钥或真实账号密码。
- 记录可定位接口失败的服务端日志，避免记录密码及会话凭证。
- 至少为权限、状态变化、并发冲突和事务回滚提供可重复执行的后端测试。
- 能在干净环境按文档启动前端、后端和数据库；部署形态另行决定，不要求付费云服务或域名。

## 10. P0 验收场景

默认准备提单人 A/B、处理人 A/B、管理员 5 个账号。测试数据应覆盖 4 种状态，并至少让一个提单人拥有 25 张工单以验证分页。各场景应使用隔离或可重置的数据，避免互相污染。

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| AC-01 | 各角色使用正确账号登录并刷新页面 | 恢复正确身份，列表范围正确 |
| AC-02 | 错误密码、未登录、会话到期，以及退出后重用旧凭证 | 按 FR-01 和错误表处理，不能继续访问受保护资源 |
| AC-03 | 提单人提交合法工单 | 生成唯一编号，状态待分配、处理人为空，存在一条创建事件 |
| AC-04 | 必填项为空、文本超限、非法枚举或注入提单人/状态字段 | 返回 `400`，不创建工单或事件 |
| AC-05 | 提单人 B 查询提单人 A 的工单及其评论、事件 | 列表不可见，直接访问统一返回 `404` |
| AC-06 | 处理人查看未分配或分配给他人的工单 | 列表不可见，直接访问返回 `404`；管理员可查看全部 |
| AC-07 | 处理人或管理员尝试创建；提单人对可见工单尝试分配 | 返回 `403`，数据不变 |
| AC-08 | 管理员把待分配工单分配给处理人 A | 状态变为处理中，A 可见，分配事件和流程版本正确 |
| AC-09 | 管理员填写原因，将处理中工单由 A 改派给 B | B 获得访问权，A 失去访问权，状态仍为处理中，历史保留 |
| AC-10 | 管理员分配给非处理人账号、相同处理人，或改派时缺少原因 | 返回 `400`，不改变工单或事件 |
| AC-11 | 当前处理人提交解决说明 | 变为已解决并记录说明；缺少说明返回 `400` |
| AC-12 | 原提单人退回已解决工单，然后再次解决并关闭 | 退回保留处理人；两次解决说明均保留；最终状态已关闭 |
| AC-13 | 已关闭工单继续评论、改派或流转 | 在通过读取及角色校验后返回 `409`，无新增记录 |
| AC-14 | 有权限的用户添加评论，包括含 HTML 标签的文本 | 未关闭工单保存成功，纯文本显示，不执行脚本；作者不可伪造 |
| AC-15 | 两个管理员会话使用同一流程版本同时分配或改派 | 只有一个成功，另一个返回 `409`，没有静默覆盖或多余事件 |
| AC-16 | 重复提交同一次解决操作 | 只产生一次状态变化和一条解决事件，重复请求返回 `409` |
| AC-17 | 测试中模拟事件写入失败 | 对应工单创建、分配或状态修改一并回滚，不出现部分成功 |
| AC-18 | 原处理人的写请求在改派生效后尝试提交 | 权限重新校验，返回 `404`，不产生评论或状态变化 |
| AC-19 | 评论和关闭并发提交 | 仅允许关闭生效之前提交成功的评论，关闭后不得追加 |
| AC-20 | 搜索、组合筛选、分页与排序 | 范围和总数不越权；25 条匹配数据按 20/5 分页；相同时间顺序稳定 |
| AC-21 | 时间线超过 20 条并加载更早记录 | 无重复或遗漏，顺序稳定；所有记录仍受工单读取权限限制 |
| AC-22 | 操作成功后刷新页面及重启后端 | 工单、评论、事件仍存在且一致 |
| AC-23 | 写请求超时或接口报错 | 不自动重发；保留输入，提示核对结果或显示明确错误 |
| AC-24 | 检查账号持久化、接口响应和业务日志 | 密码非明文存储，响应和日志不泄露密码哈希、密码及会话凭证 |

## 11. 建议实现顺序

这些阶段是学习和交付拆分，不表示需要一次完成全部前端再开发后端。

| 阶段 | 交付内容 | 重点学习 | 完成标志 |
| --- | --- | --- | --- |
| M1 身份与数据基础 | 用户初始化、数据库连接、登录/退出、当前身份、登录页 | 请求生命周期、认证、环境配置、持久化 | 5 个账号能登录，刷新和退出行为正确 |
| M2 工单读写闭环 | 创建、列表、详情、输入校验、角色数据隔离 | 数据建模、分页查询、服务端授权、错误处理 | 数据真实落库，跨账号访问被阻止 |
| M3 协作与状态流转 | 分配、改派、评论、解决、退回、关闭、时间线 | 业务状态、关联写入、事务和并发冲突 | 正常流程和退回分支均可完成 |
| M4 验证与交付 | 异常与并发测试、安全检查、初始化数据、运行文档 | 自动化测试、日志、部署和问题排查 | P0 验收通过，可按文档在干净环境运行 |

前端可临时使用 Mock 辅助布局，但 M2 起必须接入真实接口；最终验收不能依赖 Mock 或直接修改数据库来推进状态。

## 12. 后续候选与下一步

### 12.1 1.1 候选，不构成首版承诺

- 账号创建、停用和密码修改。
- 附件上传和下载权限。
- 我的待办数量与简单统计。
- 消息通知、超时提醒。
- 创建和评论的幂等提交。
- 有约束的工单内容修改，以及关闭后重新打开。

### 12.2 PRD 确认后再确定的技术事项

1. 选择后端语言与框架，以及一个关系型数据库。
2. 确定认证方式、会话失效机制、密码存储和部署安全方案。
3. 输出建表设计、索引、接口契约、统一错误结构和并发控制方案。
4. 按 M1～M4 拆解任务，每阶段完成接口验证后再推进下一阶段。

**范围原则：先把一张工单正确、安全、可追溯地处理完，再扩展功能数量。**
